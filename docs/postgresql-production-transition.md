# PostgreSQL Production Transition Runbook

This is a one-time operational procedure for moving the Artful.One production database from SQLite to PostgreSQL without losing existing data. It is not a reusable Django migration command and should not be checked into the app as management-code automation.

The current application already selects its runtime database from `DATABASE_URL` in `config/settings.py`. When `DATABASE_URL` is absent, Django uses the repository-local SQLite database `artful-one.db`. When `DATABASE_URL` is present, `dj_database_url.config()` populates both the `default` and `dashboard` database aliases. Production can therefore move to PostgreSQL by changing runtime environment only; CI and local unit tests can continue using SQLite.

At the time of writing, this repository does not include `django-import-export` as a dependency or admin integration. Use Django's existing serialization tooling (`dumpdata` and `loaddata`) for the one-time export/import unless a future branch adds a project-specific import-export workflow. Do not build a custom migration command for this cutover.

## 0. Preconditions

- Schedule a maintenance window and freeze writes before the final export. Admin edits, imports, contact submissions, filedrop changes, and photo changes must wait until the PostgreSQL deployment is verified.
- Keep the existing SQLite database and uploaded media/filedrop storage available until the PostgreSQL deployment has been verified and backed up.
- Run these commands from the same deployed image/release that will run production, so the model definitions and migrations match.
- Keep secrets out of git. All production values below are runtime environment variables or platform secrets.

Use a timestamp for every artifact:

```bash
STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
EXPORT_DIR="/tmp/artful-one-postgres-cutover-${STAMP}"
mkdir -p "${EXPORT_DIR}"
```

## 1. Record the current production database configuration

Before changing anything, capture the current runtime database setting and application revision.

```bash
python manage.py diffsettings | grep -E 'DATABASES|DJANGO|ALLOWED_HOSTS|CSRF_TRUSTED_ORIGINS' || true
git rev-parse HEAD || true
```

If the current host uses a SQLite URL, it will look like one of these existing deployment settings:

```text
DATABASE_URL=sqlite:////data/artful-one.db       # Fly.io volume
DATABASE_URL=sqlite:////storage/artful-one.db    # Single Server storage
```

If `DATABASE_URL` is unset, `config/settings.py` falls back to `artful-one.db` in the project root.

## 2. Take a physical SQLite backup first

This backup is the last-resort rollback artifact. Run it on the current production host after writes are frozen.

For Fly.io:

```bash
fly ssh console --app artful-one -C \
  "mkdir -p /data/backups && sqlite3 /data/artful-one.db \".backup '/data/backups/artful-one-pre-postgres-${STAMP}.db'\""
fly ssh sftp get --app artful-one \
  "/data/backups/artful-one-pre-postgres-${STAMP}.db" \
  "${EXPORT_DIR}/artful-one-pre-postgres-${STAMP}.db"
```

For Single Server, adjust the host and storage path as needed:

```bash
ssh <host> \
  "sqlite3 /srv/storage/artful-one/artful-one.db \".backup '/srv/storage/artful-one/artful-one-pre-postgres-${STAMP}.db'\""
scp "<host>:/srv/storage/artful-one/artful-one-pre-postgres-${STAMP}.db" "${EXPORT_DIR}/"
```

Verify the backup before proceeding:

```bash
sqlite3 "${EXPORT_DIR}/artful-one-pre-postgres-${STAMP}.db" "pragma integrity_check;"
```

The expected output is exactly:

```text
ok
```

## 3. Export logical data from the current SQLite production database

Use Django's built-in serializer so data can be loaded into PostgreSQL after migrations create the target schema.

Run this against the current production SQLite database before changing `DATABASE_URL`:

```bash
python manage.py dumpdata \
  --natural-foreign \
  --natural-primary \
  --indent 2 \
  --exclude contenttypes \
  --exclude auth.Permission \
  --exclude sessions \
  > "${EXPORT_DIR}/artful-one-${STAMP}.json"
```

Why these excludes are intentional:

- `contenttypes` and `auth.Permission` are regenerated by migrations on the PostgreSQL database; natural keys keep model references portable.
- `sessions` are transient and do not need to survive the cutover.

Optional but recommended: save table counts from the source database for comparison after import.

```bash
python manage.py shell <<'PY' > "${EXPORT_DIR}/source-counts-${STAMP}.txt"
from django.apps import apps
for model in apps.get_models():
    label = model._meta.label
    try:
        print(f"{label}\t{model.objects.count()}")
    except Exception as exc:
        print(f"{label}\tERROR\t{exc}")
PY
```

Also copy uploaded files and filedrop data if they live outside the database:

```bash
# Examples; adjust paths for the active platform.
rsync -a /data/media/ "${EXPORT_DIR}/media/"
rsync -a /data/filedrop_files/ "${EXPORT_DIR}/filedrop_files/"
```

## 4. Provision PostgreSQL

Create a dedicated database and user. Exact commands vary by provider; the database must be reachable from the production container and from the one-time import environment.

Generic PostgreSQL example:

```sql
CREATE DATABASE artful_one;
CREATE USER artful_one WITH PASSWORD 'replace-with-a-generated-secret';
ALTER ROLE artful_one SET client_encoding TO 'utf8';
ALTER ROLE artful_one SET default_transaction_isolation TO 'read committed';
ALTER ROLE artful_one SET timezone TO 'UTC';
GRANT ALL PRIVILEGES ON DATABASE artful_one TO artful_one;
```

For PostgreSQL 15+ with a locked-down `public` schema, also run inside the new database:

```sql
GRANT USAGE, CREATE ON SCHEMA public TO artful_one;
```

The production `DATABASE_URL` should use the existing `psycopg2-binary` dependency and `dj-database-url` parser:

```text
DATABASE_URL=postgres://artful_one:REPLACE_ME@POSTGRES_HOST:5432/artful_one
```

Use `postgres://` or `postgresql://`; `dj-database-url` accepts both. Add provider-required SSL query parameters if needed, for example:

```text
DATABASE_URL=postgres://artful_one:REPLACE_ME@POSTGRES_HOST:5432/artful_one?sslmode=require
```

## 5. Configure production environment variables

Update runtime environment only. Do not change the CI/test configuration for this cutover.

Required database switch:

```bash
DATABASE_URL='postgres://artful_one:REPLACE_ME@POSTGRES_HOST:5432/artful_one?sslmode=require'
```

Keep or set the existing production settings:

```bash
DJANGO_SECRET='existing-production-secret'
DJANGO_DEBUG='false'
ALLOWED_HOSTS='artful.one,www.artful.one'
CSRF_TRUSTED_ORIGINS='https://artful.one,https://www.artful.one'
```

Keep storage paths appropriate to the deployment target:

```bash
# Fly.io examples
STATIC_ROOT='/data/staticfiles'
MEDIA_ROOT='/data/media'
FILEDROP_BASE_DIR='/data/filedrop_files'

# Single Server examples
MEDIA_ROOT='/storage/media'
FILEDROP_BASE_DIR='/storage/filedrop_files'
```

Keep optional provider secrets unchanged when those features are in use:

```bash
MAILGUN_API_KEY='...'
MAILGUN_DOMAIN='...'
MAILGUN_FROM_EMAIL='...'
CONTACT_EMAIL='...'
CLOUDFLARE_EMAIL='...'
CLOUDFLARE_TOKEN='...'
CLOUDFLARE_ZONE_ID='...'
OPENROUTER_API_KEY='...'
SCREENSHOT_SECRET='...'
SENTRY_DSN='...'
```

Do not set `DISABLE_AUTOCOMMIT` unless there is a separate operational reason; `config/settings.py` only uses it as an explicit override.

## 6. Initialize the empty PostgreSQL schema

Run migrations with `DATABASE_URL` pointing to the new PostgreSQL database.

```bash
export DATABASE_URL='postgres://artful_one:REPLACE_ME@POSTGRES_HOST:5432/artful_one?sslmode=require'
export DJANGO_SECRET='existing-production-secret'
export DJANGO_DEBUG='false'

python manage.py check
python manage.py migrate --noinput
```

This creates the PostgreSQL schema, content types, and permissions before data import.

## 7. Import the exported data into PostgreSQL

Load the JSON fixture into the migrated PostgreSQL database:

```bash
python manage.py loaddata "${EXPORT_DIR}/artful-one-${STAMP}.json"
```

If the import fails, stop and investigate before cutting over traffic. Do not partially cut over. The SQLite source backup and JSON export should remain unchanged.

After a successful import, rebuild derived/search data if needed:

```bash
python manage.py reindex_all
```

Then collect static files for the active deployment target if the entrypoint does not already do it:

```bash
python manage.py collectstatic --noinput
```

## 8. Verify PostgreSQL before traffic cutover

First confirm Django is actually connected to PostgreSQL:

```bash
python manage.py shell <<'PY'
from django.db import connection
print(connection.vendor)
print(connection.settings_dict['ENGINE'])
print(connection.settings_dict['NAME'])
PY
```

Expected vendor is `postgresql`, and the engine should be `django.db.backends.postgresql`.

Compare model counts against the source counts saved before import:

```bash
python manage.py shell <<'PY' > "${EXPORT_DIR}/postgres-counts-${STAMP}.txt"
from django.apps import apps
for model in apps.get_models():
    label = model._meta.label
    try:
        print(f"{label}\t{model.objects.count()}")
    except Exception as exc:
        print(f"{label}\tERROR\t{exc}")
PY

diff -u "${EXPORT_DIR}/source-counts-${STAMP}.txt" "${EXPORT_DIR}/postgres-counts-${STAMP}.txt"
```

Some differences are acceptable for regenerated framework tables such as content types, permissions, and sessions. User content tables should match, especially:

- `blog.Entry`, `blog.Blogmark`, `blog.Quotation`, and `blog.Note`
- `blog.Comment`, `blog.Tag`, `blog.PreviousTagName`, `blog.Series`, and `blog.LiveUpdate`
- `blog.Photo`, `blog.PhotoTag`, and `blog.Photoset`
- `blog.ContactMessage`
- `feedstats.SubscriberCount`
- `monthly.Newsletter`
- `filedrop.Drop`, `filedrop.Token`, and `filedrop.DownloadLog`
- `rpg.RpgTable` and `rpg.RpgTableAlias`
- `sketches.Sketch` and `sketches.Animation`

Run application checks:

```bash
python manage.py check
python manage.py validate_entries_xml
```

Smoke test the deployed app while it points at PostgreSQL:

```bash
curl -fsS https://artful.one/health/
```

Also verify manually:

- Homepage renders.
- Admin login works with an existing superuser.
- Blog entries, tags, archives, search, feeds, photo pages, sketches, RPG pages, filedrop, and contact form work.
- Recent uploaded media and filedrop downloads are present.
- New admin write test succeeds, then remove the test object if one was created.
- Error logs are clean after requests.

## 9. Final cutover

Only after the verification checklist passes:

1. Keep writes frozen on the old SQLite deployment.
2. Confirm the final JSON export timestamp is the one imported into PostgreSQL.
3. Deploy/restart production with the PostgreSQL `DATABASE_URL`.
4. Run `/health/` and the smoke checks again on the public domain.
5. Keep the SQLite backup, JSON export, source counts, and PostgreSQL counts in the incident/change record.

If verification fails before traffic cutover, switch `DATABASE_URL` back to the previous SQLite value and restart the old deployment. If failure happens after cutover, freeze writes immediately, decide whether any PostgreSQL-only writes must be preserved manually, then restore the old SQLite environment only if data ownership is clear.

## 10. Backups after PostgreSQL is live

Replace the SQLite backup cron with provider-native PostgreSQL backups or a `pg_dump` job. Example logical backup:

```bash
pg_dump "$DATABASE_URL" --format=custom --file "artful-one-${STAMP}.dump"
pg_restore --list "artful-one-${STAMP}.dump" >/dev/null
```

Periodically test restore into a temporary PostgreSQL database and run the same smoke checks against it.

## CI and unit tests stay on SQLite

Do not set `DATABASE_URL` for normal local unit tests or CI unless a specific job is meant to exercise PostgreSQL. With no `DATABASE_URL`, `config/settings.py` keeps using SQLite:

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": "artful-one.db",
    }
}
```

The existing Docker test target already forces in-memory SQLite:

```bash
docker run --rm \
  -e DJANGO_SECRET=test-secret-key-for-checks-and-verification \
  -e DATABASE_URL=sqlite:///:memory: \
  ghcr.io/bkroeze/artful-one:latest \
  uv run pytest
```

That separation is intentional: production uses PostgreSQL through runtime `DATABASE_URL`, while CI/unit tests continue using SQLite for speed and compatibility.
